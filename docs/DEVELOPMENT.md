# Разработка и выпуск

## Окружение и проверки

Эталон окружения — [Backend CI](../.github/workflows/backend-ci.yml),
[Frontend CI](../.github/workflows/frontend-ci.yml) и
[сборка пакетов](../.github/workflows/build.yml) в Ubuntu 24.04, Node.js 22.
Backend требует ucode с fs/UCI; версии libubox, UCI и ucode закреплены в workflow.
`tools/provision-test-cores.py` скачивает официальные ядра с закреплёнными SHA256
в изолированный каталог, не заменяя установленный системный sing-box.

```sh
python3 tools/provision-test-cores.py
FORKOP_REQUIRE_CURRENT_CORES=1 bash tests/run-backend.sh
```

Отчёты сохраняются в `/tmp/forkop-test-report-*` либо
`FORKOP_TEST_REPORT_DIR`. Обязательный режим не позволяет пропустить тесты
с опубликованными ядрами. Нативные тесты протоколов требуют Linux amd64.

```sh
cd fe-app-forkop
corepack enable
corepack prepare pnpm@11.25.0 --activate
pnpm install --frozen-lockfile
pnpm exec prettier --check src
pnpm run lint --max-warnings=0
pnpm test --run
pnpm run build
```

Изменение поведения начинают с поведенческого теста и наблюдавшегося RED,
затем исправляют реализацию и получают GREEN. Команды и результаты записывают
в `docs/tdd`. Обновление документации не меняет runtime-поведение.
Запрещено считать недоступную проверку успешной или подменять реальные
испытания анализом текста исходника. До слияния нужен независимый review.

## Пакеты

```sh
bash build.sh 1.2.0
```

По умолчанию шесть пакетов появляются в `dist/release-final`. Сборка требует
Linux, fakeroot, пользовательских пространств имён и инструментов из `build.sh`.
SDK OpenWrt проверяются по SHA256; инструмент переводов собирается из
закреплённого коммита LuCI. Backend, LuCI и перевод выпускаются в IPK и APK.
Ядро sing-box не встраивается в эти переносимые пакеты.

## Порядок выпуска

1. Согласовать `VERSION`, описание `docs/releases/<версия>.md` и README;
   проверить ссылки, совместимость и список ограничений. Не править опубликованный тег.
2. Дождаться зелёной сборки PR с backend/frontend gates и ShellCheck;
   слить проверенный head в `m0llusca/forkop-next/main`, сохранив новые записи регрессионных проверок.
3. В Actions → Build packages запустить workflow на **main** с
   `release_tag=1.2.0` и описанием выпуска из документа выше.
   Dispatch публикует релиз автоматически после gates и сборки;
   простой push в main пакетный релиз не создаёт. Push тега тоже публикует релиз.
4. Убедиться, что head workflow, тег и main указывают на выбранный коммит.
   В workflow проверяются версии и зависимости всех шести пакетов.
   Скачать опубликованные файлы, проверить их SHA256 и payload IPK против
   исходников именно этого коммита. Проверка APK в сборке относится к метаданным.
5. Подготовить `SHA256SUMS.txt` из окончательных шести файлов и приложить к
   релизу. В отдельном манифесте сохранить commit, тег, workflow URL и хеши.
   GitHub добавляет архивы исходников по тегу автоматически.
6. Проверку устройства выполнять отдельно по `docs/ACCEPTANCE.md`.
   Зелёный CI не означает, что состоялось развёртывание на роутере или VPS.

Не использовать старые PR-артефакты как доказательство идентичности финального
релиза без сверки. Не включать токены, серверные ключи, полные экспорты профилей
или частные сетевые дампы в логи и выпуск.
